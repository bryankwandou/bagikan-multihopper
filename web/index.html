Pay forty wallets in one run, not one afternoon.

01 · Problem

Every campaign ends with a spreadsheet and a wallet.

Creator campaigns, bounties, hackathons and DAO grants all finish the same way: one treasury, a list of 30 to 200 wallets, and someone pasting addresses into a wallet app one at a time.

A

It is slow

Forty recipients means forty copy, paste, check, sign cycles. The person doing it usually has other work waiting.

B

One typo is final

A wrong character sends funds to a wallet nobody controls. There is no chargeback and no support desk.

C

The treasury reads like a rate card

Every direct payout from one wallet is public. Anyone with an explorer can list who you paid, how much, and when.

02 · How it works

Four API calls per batch, signed in a fixed order.

Hoproll is a thin layer over the MultiHopper API. It never holds funds: the treasury owner signs, MultiHopper's keeper network executes the route on-chain.

Validate and batch the CSV

Base58 address check, duplicates merged, amounts converted to raw units with BigInt so shares add up exactly. Lists over 20 become several batches.

wallet,amount,note 7xKp…q9Ld,1.25,creator-1 → batch 0 (20) · batch 1 (20) · batch 2 (3)

Quote, then create

The estimate shows the fee before anyone signs. Each batch is created with its own externalId and an Idempotency-Key, so a double click never creates a second transfer.

POST /transfers/estimate { destinationCount: 20 } POST /transfers { destinations[≤20], hops, arrivalSeconds, externalId }

Sign in the order the docs require

The keeper funding transaction is signed and recorded first. Then route, orchestrator, session and dispersion. Groups that come back null are already on-chain and are skipped.

POST /transfers/:id/prepare keeperFundingTx → routeInitTxs → orchestratorInitTx → sessionInitTxs → dispersionInitTxs

Confirm and record evidence

Broadcast is confirmed in two stages. Status per recipient moves from pending to paid, read from the transfer or from a signed webhook.

POST /transfers/:id/confirm-broadcast GET /transfers/:id · webhook transfer.completed x-multihopper-signature: HMAC-SHA256
03 · Compared

Bulk senders already exist. Routing is the gap.

Tools like Multisender and Streamflow Payouts already take a CSV and pay many wallets. Hoproll does not try to beat them on batch size. It adds what a direct send cannot: multi-hop routing, a chosen arrival time, compliance screening, and an evidence file per wallet.

Manual, one by oneCSV bulk sendersHoproll on MultiHopper
CSV importNoYesYes
Recipients per transfer1Many, split across transactionsUp to 20 per Multi-Send, auto-batched

Compliance screeningNoNot in the public docs we readTRM Labs screening on mainnet
Per-wallet evidence for financeManual notesPayout history (Streamflow)CSV: transfer ID, signature, time, amount
CostNetwork feesVaries by tool0.5% + 0.002 SOL per screened wallet

Sources: MultiHopper developer docs (multi-destination, prepare, pricing), Streamflow Payouts help article, read 31 Oct 2026. Routing reduces simple linkage between a treasury and its recipients. It does not guarantee anonymity, and Hoproll does not market it that way.

Who it is for

  • Agencies and projects paying creators and KOLs after a campaign
  • Bounty and hackathon organisers paying winners
  • DAOs sending grants, small teams paying contributors

What it will not do

  • Hold your funds or your keys. The treasury owner signs.
  • Promise anonymity. Routing reduces simple linkage, nothing more.
  • Hide fees. The quote is shown before the first signature.
